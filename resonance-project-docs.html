1Project Overview & Value Proposition

Resonance is a production-ready text-to-speech and voice cloning platform that serves as an alternative to ElevenLabs. Instead of paying per-character API fees, organizations self-host the open-source Chatterbox TTS model and only pay for GPU compute time.

Core Value Proposition

The app provides a complete SaaS experience with multi-tenancy, billing, and secure file storage — but the voice generation itself runs on rented GPUs rather than through a third-party API. This gives organizations full control over their voice data and cost model.

3Data Model (Prisma Schema)

Source: prisma/schema.prisma

Models & Relationships

model Voice {
  id          String        @id @default(cuid())
  orgId       String?       // NULL for SYSTEM voices, set for CUSTOM
  name        String?       // "Narrator", "Customer Service Pro", etc.
  description String?       // Optional human-readable description
  variant     VoiceVariant  // SYSTEM | CUSTOM
  category    VoiceCategory // AUDIOBOOK | CONVERSATIONAL | etc.
  language    String?       @default("en-US")
  r2ObjectKey String?       // Path to reference audio in R2
  generations Generation[]   // One-to-many: voice → many generations
  createdAt   DateTime      @default(now())
  updatedAt   DateTime      @updatedAt

  @@index([variant])   // Fast filter: system vs custom
  @@index([orgId])      // Fast filter: by organization
}

model Generation {
  id        String   @id @default(cuid())
  orgId     String   // ALWAYS set (scoped to org)
  voiceId   String?  // References Voice (can be null if deleted)
  voice     Voice?   @relation(fields: [voiceId], references: [id], onDelete: SetNull)
  text      String   // The input text that was spoken
  voiceName String   // Snapshot of voice name at generation time
  r2ObjectKey String? // Path to generated audio in R2
  temperature    Float  // 0.0 - 2.0
  topP           Float  // 0.0 - 1.0
  topK           Int    // 1 - 10000
  repetitionPenalty Float // 1.0 - 2.0
  createdAt   DateTime @default(now())
  updatedAt   DateTime @updatedAt

  @@index([orgId])    // Fast filter: by organization
  @@index([voiceId])  // Fast reverse lookup: voice → generations
}

Enums

enum VoiceVariant {
  SYSTEM    // Shared across all orgs (the 20 built-in voices)
  CUSTOM    // Uploaded by a specific organization
}

enum VoiceCategory {
  AUDIOBOOK, CONVERSATIONAL, CUSTOMER_SERVICE, GENERAL, NARRATIVE,
  CHARACTERS, MEDITATION, MOTIVATIONAL, PODCAST, ADVERTISING,
  VOICEOVER, CORPORATE
}

Key Design Decisions in the Schema

  • Soft relationship via SetNull: If a Voice is deleted, its Generations remain with voiceId: null — you keep the audio but unlink the voice. This preserves generation history.
  • orgId on both tables: Multi-tenancy enforced at the database level — no cross-org data leakage even if API logic has bugs.
  • VoiceName snapshot: Generation.voiceName stores a copy of the voice name at generation time. If the voice is later renamed or deleted, the generation's metadata is preserved.
  • r2ObjectKey nullable on Generation: Allows for the atomic two-phase pattern — create record first, upload audio, then link.
  • cuid() IDs: Collision-resistant, short, URL-safe. Generated client-side, so we know the ID before the DB write completes.

Step 3: Authentication (orgProcedure middleware)

Backend: src/trpc/init.ts:48

// This middleware wraps EVERY protected endpoint
export const orgProcedure = baseProcedure.use(async ({ next }) => {
  const { userId, orgId } = await auth();  // Clerk server-side auth
  if (!userId) throw new TRPCError({ code: "UNAUTHORIZED" });
  if (!orgId)  throw new TRPCError({ code: "FORBIDDEN", message: "Organization required" });
  return next({ ctx: { userId, orgId } });  // Available in all downstream
});

The middleware calls Clerk's server-side auth(), which extracts the session token from the request. If there's no user or no organization, the request is rejected before any business logic runs.

Step 4: Billing Check (Paywall)

Backend: src/trpc/routers/generations.ts:59

try {
  const customerState = await polar.customers.getStateExternal({
    externalId: ctx.orgId,
  });
  const hasActiveSubscription = (customerState.activeSubscriptions ?? []).length > 0;
  if (!hasActiveSubscription) {
    throw new TRPCError({
      code: "FORBIDDEN",
      message: "SUBSCRIPTION_REQUIRED",
    });
  }
} catch (err) {
  if (err instanceof TRPCError) throw err;
  // Customer doesn't exist in Polar yet → no subscription
  throw new TRPCError({ code: "FORBIDDEN", message: "SUBSCRIPTION_REQUIRED" });
}

This prevents free orgs from generating audio. The frontend catches "SUBSCRIPTION_REQUIRED" and shows a "Subscribe" button in the toast.

Step 5: Voice Lookup (Multi-tenant)

Backend: src/trpc/routers/generations.ts:81

const voice = await prisma.voice.findUnique({
  where: {
    id: input.voiceId,
    OR: [
      { variant: "SYSTEM" },                    // Anyone can use system voices
      { variant: "CUSTOM", orgId: ctx.orgId }   // Only this org's custom voices
    ],
  },
  select: { id: true, name: true, r2ObjectKey: true },
});
if (!voice) throw new TRPCError({ code: "NOT_FOUND", message: "Voice not found" });

This OR filter is the critical security boundary — it ensures org A can never access org B's custom voice uploads. The r2ObjectKey is where the voice's reference audio lives in R2.

// The Python service receives this and runs:

The chatterbox client is an openapi-fetch instance with the API key pre-configured. It receives raw WAV bytes back as an ArrayBuffer. The Python service loads the Chatterbox model on an A10G GPU on Modal, runs the generation, and streams back the WAV file.

Step 7: Storage (Create → Upload → Link)

Backend: src/trpc/routers/generations.ts:147 + src/lib/r2.ts

// PHASE 1: Create DB record first (without audio)
const generation = await prisma.generation.create({
  data: {
    orgId: ctx.orgId,
    text: input.text,
    voiceName: voice.name || "",
    voiceId: voice.id,
    temperature: input.temperature,
    topP: input.topP,
    topK: input.topK,
    repetitionPenalty: input.repetitionPenalty,
  },
  select: { id: true },  // We only need the ID now
});

// PHASE 2: Generate R2 key using the DB-generated ID
const r2ObjectKey = `generations/orgs/${ctx.orgId}/${generation.id}`;

// PHASE 3: Upload WAV to R2
await uploadAudio({ buffer, key: r2ObjectKey });

// PHASE 4: Link the R2 key back to the record
await prisma.generation.update({
  where: { id: generation.id },
  data: { r2ObjectKey },
});

Why this order? We need the database-generated ID to construct a deterministic R2 path. By creating the record first, we get a stable ID. If the upload fails in Phase 3, the catch block deletes the orphanced DB record, leaving no data inconsistency.

R2 Upload: [src/lib/r2.ts](src/lib/r2.ts) uses the AWS S3 SDK (PutObjectCommand) pointed at Cloudflare R2. The client is initialized with R2 credentials and the bucket name from environment variables.

Step 8: Billing Meter (Fire-and-Forget)

Backend: src/trpc/routers/generations.ts:212

// Report usage to Polar for billing
polar.events
  .ingest({
    events: [
      {
        name: "tts_generation",
        externalCustomerId: ctx.orgId,
        metadata: { characters: input.text.length },

This reports how many characters the org consumed. The .catch() means billing errors never break TTS generation — the user always gets their audio even if metering fails.

Step 10: Playback

// Browser navigates to /text-to-speech/{id}
// WaveSurfer hook fetches /api/audio/{id}
// Server route (src/app/api/audio/[generationId]/route.ts):
const { userId, orgId } = await auth();

The audio is streamed through a secure proxy — the browser never sees R2 credentials or direct URLs.

5Storage & Security Architecture

Cloudflare R2: The Audio Bucket

src/lib/r2.ts — All audio lives here, private by default.

// R2 client initialized with S3-compatible endpoint
const r2 = new S3Client({
  region: "auto",
  endpoint: `https://${env.R2_ACCOUNT_ID}.r2.cloudflarestorage.com`,
  credentials: {
    accessKeyId: env.R2_ACCESS_KEY_ID,
    secretAccessKey: env.R2_SECRET_ACCESS_KEY,
  },
});

// Upload (server-side only)
async function uploadAudio({ buffer, key, contentType = "audio/wav" }): Promise {
  await r2.send(new PutObjectCommand({
    Bucket: env.R2_BUCKET_NAME,
    Key: key,
    Body: buffer,
    ContentType: contentType,
  }));
}

// Presigned URL (temporary, time-limited access)
async function getSignedAudioUrl(key: string): Promise {
  const command = new GetObjectCommand({
    Bucket: env.R2_BUCKET_NAME,
    Key: key,
  });
  return getSignedUrl(r2, command, { expiresIn: 3600 }); // 1 hour
}

Interview Question: Why did you need presigned URLs?

The problem: Cloudflare R2 (like AWS S3) stores objects privately by default. If we put a generated .wav in a private bucket and gave the browser a direct R2 URL, we'd need to either:

  1. Make the bucket public — then anyone could download anyone's audio by guessing keys. Terrible security.
  2. Embed R2 credentials in the frontend — even worse, credentials in the browser are fully exposed.

The solution: presigned URLs. The server (which has credentials) generates a temporary, single-use URL that grants time-limited download access to one specific file:

// 1. User requests /api/audio/gen_123 from the browser
// 2. Server checks: is the user logged in? Which org?
// 3. Server checks: does generation gen_123 belong to this org?
// 4. Server generates a 1-hour presigned URL:
const signedUrl = await getSignedAudioUrl("generations/orgs/org_xyz/gen_123");
// 5. Server fetches the audio and streams it through (proxy)
// 6. Browser gets the WAV bytes without ever seeing R2 credentials

// Even better: the signed URL could be sent directly to the browser
// for client-side downloads. But proxy is more secure (still checks auth).

Properties of presigned URLs:

  • Time-limited: Expires after 1 hour (configurable)
  • Scope-limited: Only works for the specific object/key, not the whole bucket
  • No credential exposure: Browser never sees R2 access key or secret
  • Revocable: If leaked, it self-destructs after the TTL expires

This is the standard S3/R2 pattern for private object access. It balances security with performance — the browser downloads directly from the CDN edge rather than proxying through your server.

Alternatives: (1) Proxy all audio through the server (secure but bandwidth-heavy), (2) Sign cookies for browser sessions (complex), (3) Use R2's S3-compatible auth tokens (works but exposes more attack surface).

💡 Key Insight: Presigned URLs scale because the browser downloads directly from R2's CDN edge — your Next.js server isn't in the download path at all (just generates the URL).

7Interview Q&A (Prepared Answers)

Q1: Why did you choose Modal instead of running the model on AWS?

Answer: Modal provides serverless GPU compute. You write Python code and Modal handles GPU provisioning, scaling, and teardown. Key benefits:

  • No idle cost: Instances scale to zero after 5 minutes idle and spin up on the next request
  • No DevOps: No SSH, no Docker management, no instance monitoring — just deploy code
  • Pay-per-use: You pay per second of GPU time (~$0.001/sec for A10G), not per hour
  • Concurrency: Each warm instance handles 10 concurrent generations via @modal.concurrent

The trade-off: Less control. With AWS EC2, you'd manage a g4dn.xlarge (~$0.50/hr) 24/7 or build custom autoscaling. You'd also handle SSH, updates, and uptime. Modal trades control for simplicity.

💡 Key Insight: Modal is perfect for intermittent GPU workloads — you pay $0.0007/sec only while generating, vs $0.50/hr for an always-on EC2 instance.

Alternatives: RunPod (cheaper GPUs, more manual), Replicate (pre-built models), AWS Lambda GPU (limited), or bare EC2 for maximum control.

Q2: What exactly happens when a user submits text?
See the full Request Flow section above. In 30 seconds: 
1. Form validates (TanStack Form + Zod)
2. Auth middleware checks Clerk (userId, orgId)
3. Billing check against Polar (active subscription?)
4. Voice lookup in PostgreSQL (SYSTEM or own CUSTOM)
5. HTTP POST to Modal GPU → raw WAV bytes
6. Create DB record → Upload to R2 → Link record
7. Fire-and-forget usage event to Polar
8. Return { id } → Browser redirects → WaveSurfer playback
Q3: Why FastAPI for the GPU service (not Flask, Node.js)?

Answer: FastAPI is the modern standard for Python web services because:

  • Pydantic v2 validation: The TTSRequest model (prompt, voice_key, temperature, etc.) is validated at the framework level — malformed requests never reach the GPU.
  • Async support: FastAPI runs on Starlette/uvicorn, which natively supports async. This means GPU-bound work doesn't block the event loop.
  • Auto-generated docs: /docs and /redoc endpoints are auto-generated — great for testing and debugging.
  • Type-safe: Python type hints on request/response models give IDE autocomplete and error detection.
  • Chatterbox is Python: The model library is PyTorch-based Python. FastAPI is the path of least resistance — no language bridging required.

Alternatives: Flask (synchronous, no built-in validation, needs Flask-RESTful for structured APIs), Django REST Framework (heavier, ORM-coupled), or just raw uvicorn with manual routing. FastAPI is the sweet spot for Python ML services.

Q4: What is tRPC doing here and why not just use REST?

Answer: tRPC eliminates the need for a separate API contract layer. Here's the difference:

// REST approach (traditional):
// 1. Write API endpoint in Next.js API routes
app.post("/api/generate", async (req, res) => { ... });

// 2. Write OpenAPI spec manually or generate it
// 3. On frontend, make raw HTTP calls:
const res = await fetch("/api/generate", { method: "POST", body: JSON.stringify(data) });
const json = await res.json(); // No type safety!

// 4. Optionally generate types from OpenAPI — extra step, easy to drift

// tRPC approach (current):
// 1. Define procedure ONCE on server:
const generationsRouter = createTRPCRouter({
  create: orgProcedure.input(z.object({...})).mutation(async ({ input, ctx }) => {
    // ... typed input, typed context
    return { id: "gen_123" };
  })
});

// 2. Call directly from frontend (fully typed!):
const { id } = await trpc.generations.create.mutateAsync({ text: "...", voiceId: "..." });
// TypeScript knows: input shape, return type, error shape — all inferred automatically

The key benefit: If you change the input schema on the server (e.g., add a required field), the frontend immediately gets a compile-time error. With REST, you'd only find out at runtime.

Alternatives: REST with OpenAPI code generation (extra build step, can drift), GraphQL (single endpoint, but adds complexity for simple CRUD), or raw HTTP (no types, manual validation). tRPC wins for TypeScript-only apps with tight frontend/backend teams.

💡 Key Insight: tRPC's type inference happens at compile time — if your server returns { id: string }, your frontend gets const { id }: { id: string } automatically. No OpenAPI syncing needed.
Q5: Why PostgreSQL and not MongoDB/Redis/DuckDB?

Answer: PostgreSQL for five reasons specific to this project:

  • Relational data: Generation has a foreign key to Voice. If you use MongoDB, you'd either denormalize (duplicating voice data) or do client-side joins (inefficient). PostgreSQL handles this natively.
  • Multi-tenant indexing: Every query filters by orgId. PostgreSQL's @@index([orgId]) annotations ensure fast tenant isolation. The same pattern is awkward in NoSQL.
  • ACID transactions: Billing and meter events must be consistent. PostgreSQL's transaction support ensures a generation record + usage event either both succeed or both fail. Redis and MongoDB have weaker guarantees here.
  • Prisma ecosystem: Prisma (the ORM used) has its most mature, type-safe, and documented integration with PostgreSQL. The query builder is cleanest with Postgres as the target.
  • Cloud pricing: PostgreSQL is offered by every cloud provider (Supabase, Neon, AWS RDS, Google Cloud SQL). It's the lowest-friction hosted option.

Alternatives: PlanetScale (MySQL-based, serverless, but no foreign key constraints), MongoDB (if you anticipated heavily semi-structured data), or even Supabase (which bundles Postgres with auth for a simpler setup). For this use case, Postgres is the right call.

Q6: Why Prisma instead of raw SQL/DRIZZLE/Knex?

Answer: Prisma provides schema-first development with auto-generated TypeScript types:

// prisma/schema.prisma

  temperature     Float
  topP            Float
  topK            Int
  repetitionPenalty Float

  @@index([orgId])

// 2. Query with full type safety:
const gen = await prisma.generation.create({
  data: {
    orgId: ctx.orgId,       // ✅ string
    text: input.text,       // ✅ string

Alternatives: (1) Drizzle ORM — lighter bundle, SQL-like syntax, but less schema-first DX. (2) Knex — just a query builder, no models or types. (3) Raw pg — fastest but no type safety. For TypeScript-first teams shipping fast, Prisma is the most productive choice.

Q7: What is multi-tenancy and how did you implement it?

Multi-tenancy means multiple organizations share one application instance, but their data is strictly isolated. In Resonance, data isolation is enforced at six layers — defense in depth:

// 1. AUTH LAYER (src/trpc/init.ts) — orgProcedure middleware:
const { userId, orgId } = await auth();     // Clerk injects orgId
if (!orgId) throw new TRPCError({ code: "FORBIDDEN" });  // Required

// 2. DATABASE LAYER (prisma/schema.prisma):
model Generation {
  orgId String                            // Column on every table
  @@index([orgId])                         // Index for fast tenant queries
}

// 3. QUERY LAYER — Every query filters by orgId:
prisma.generation.findMany({ where: { orgId: ctx.orgId } })
prisma.generation.create({ data: { orgId: ctx.orgId } })
prisma.generation.update({ where: { id, orgId: ctx.orgId } })  // Ownership check on updates

// 4. STORAGE LAYER — R2 keys are org-scoped:
generations/orgs/{orgId}/{generationId}.wav
voices/orgs/{orgId}/{voiceId}.wav

// 5. VOICE ACCESS — SYSTEM voices are global, CUSTOM are org-only:
prisma.voice.findUnique({
  where: {
    id: voiceId,
    OR: [
      { variant: "SYSTEM" },                    // Shared by everyone
      { variant: "CUSTOM", orgId: ctx.orgId }   // Only this org
    ]
  }
})

// 6. AUDIO PLAYBACK — Signed URLs with ownership check:
// src/app/api/audio/[id]/route.ts
const gen = await prisma.generation.findUnique({ where: { id, orgId } });
if (!gen) return 404;  // Can't access other org's audio

Why six layers? Each is an independent check. A bug in the query layer (missing orgId filter) is caught by the storage key prefix. A bug in the R2 path construction is caught by the DB ownership check. This is defense in depth — not single-point-of-failure security.

Q8: Why presigned URLs instead of just serving from the server?

Already answered above in the Storage & Security section. In short: private R2 bucket + temporary access URL = secure and efficient. The alternative (proxying all audio through the Next.js server) doubles bandwidth costs and adds latency.

Q9: What happens if the GPU request fails?

Multiple failure paths are handled:

// 1. GPU returns error (5xx or timeout):
const { data, error } = await chatterbox.POST("/generate", { ... });
if (error) {
  throw new TRPCError({ code: "INTERNAL_SERVER_ERROR", message: "Failed to generate audio" });
}
// → Frontend catches, shows toast: "Failed to generate audio"

// 2. Upload to R2 fails:
try {
  const gen = await prisma.generation.create({ data: { ... } });  // DB row created
  await uploadAudio({ buffer, key: r2Key });                       // Upload fails
} catch {
  if (generationId) {
    await prisma.generation.delete({ where: { id: generationId } }).catch(() => {});
  }  // Cleanup orphan DB record
  throw new TRPCError({ code: "INTERNAL_SERVER_ERROR", message: "Failed to store generated audio" });
}

// 3. Polar billing event fails (fire-and-forget):
polar.events.ingest({ events: [...] })
  .catch(() => { /* silently ignored — user still gets audio */ });

// 4. Unhandled errors (Sentry):
// orgProcedure wraps everything with Sentry.trpcMiddleware({
//   attachRpcInput: true  // Logs full request input for debugging
// });

Key principle: The user either gets their audio successfully, or they get a clear error. There are no half-finished states (no generation record without audio, no audio without a record). The create-then-upload pattern with rollback ensures this.

Q10: What is temperature in TTS generation?

Based on my knowledge of ML generation:

Temperature controls the randomness of the model's output by scaling the logits/probability distribution before sampling. In the context of voice generation, it affects:

  • Low (0.0 - 0.5): Near-deterministic. Each generation sounds very similar. Can sound robotic or monotone. Good for when you need consistent, reproducible output.
  • Medium (0.6 - 1.0): Balanced variety. Natural inflection, some variation between generations. This is the sweet spot for most use cases.
  • High (1.2 - 2.0): High variability. Each generation can sound quite different. Can produce more expressive speech but risks instability — artifacts, inconsistent tone, or the model going off-distribution.

In Chatterbox specifically (a diffusion-based TTS model), temperature likely modifies the sampling from the model's output probability distribution at each generative step. The default of 0.8 in the code is a reasonable starting point — expressive but stable.

Q11: What does top-k do?

Answer: Top-k sampling restricts the model's choices at each generation step to the k most likely options, then samples from that restricted set.

// How it works conceptually:
// At each step, the model produces logits for all possible next tokens/phonemes
// Without top-k: sample from full distribution (1000s of options)
// With top-k=1000: filter to top 1000 most likely, renormalize, sample

// Low k (10-50): Very focused. Output stays close to the expected path.
//   - Pro: Reproducible, consistent, controllable
//   - Con: Can sound robotic, less natural variation

// High k (500-1000): More exploration. Wider range of outputs.
//   - Pro: More natural-sounding, creative
//   - Con: Less predictable, may diverge

// k = 1: Greedy decoding. Always pick the single most likely option.
//   - Most deterministic, least natural

Difference from temperature: Temperature changes the shape of the probability distribution (sharpening or flattening it). Top-k changes the set of candidates (filtering, not scaling). They're orthogonal and often used together — top-k filters the candidates, temperature scales their probabilities.

The code defaults to topK: 1000 and temperature: 0.8 — a combination that provides good quality with reasonable determinism. For voice, you typically want some variation for naturalness but not so much that the voice becomes inconsistent.

Q12: Where does the audio actually live?

All audio files live in Cloudflare R2, a private object storage bucket named resonance-app. There are two types of audio:

// 1. Reference voice clips (for cloning)
voices/system/narrator.wav           ← 20 built-in voices (shared, read-only R2 mount)
voices/orgs/org_xyz/voice_abc.wav    ← Custom voices uploaded by orgs

// 2. Generated audio output
generations/orgs/org_xyz/gen_abc.wav ← TTS output (public-read via signed URL)

Access control: The R2 bucket is private. Audio files are never directly accessible via a URL — they're only served through the /api/audio/[id] proxy route, which verifies org ownership and generates a time-limited presigned URL.

Reference audio: System voices are loaded into the Modal GPU service via a read-only R2 mount at /r2. The voice_key in generation requests is actually the R2 path (e.g., voices/system/narrator.wav).
